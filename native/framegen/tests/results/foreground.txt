The engine beside a GPU-bound game that is the window in front (RTX 3060, Windows 11 26200,
hardware GPU scheduling off, 2026-11-10).

Why this was measured: all 24 recorded real-game sessions (Star Citizen, Once Human, Wardogs) had
fewer output frames than source frames, and the four run logs show the screen at 2 to 8 fps for 5 to
10 s before the automatic stop, with one analysis spanning 45 to 240 ms of GPU time and Present
waiting 200 to 900 ms. Every earlier stand-in test passed because the stand-in game was never the
foreground window (--always-active). Windows gives the GPU to the foreground program first.

Method: a stand-in game (one heavy pixel shader in 16 draws per frame, no frame cap, 1920x1080,
calibrated to 35 fps with the GPU at 100%) takes the keyboard focus; the engine is started as the
app starts it (--mode auto --max-mul 4 --quality balanced --capture wgc, no --always-active) on a
60 Hz monitor, 9 s per case. src/out are the engine's counters, game = the stand-in's own count,
shown = Present calls in the half second.

Read: at the default priority the foreground game starves the engine the way the real logs show
(4 fps against 35 from the game). With its own GPU class raised the engine holds 60 fps on the
60 Hz monitor and the game gives up 2 to 4 of 35 fps. With the trial run, the starved case never
reaches the screen and the game keeps its 34 fps.

Not measured: a real game (Windows Game Mode registers real games and applies its own graphics
priority to them; the stand-in is only the foreground window), a 144 Hz monitor in this condition,
hardware GPU scheduling on (the engine then asks for the high class, not realtime), other GPUs.
