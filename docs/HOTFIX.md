# 긴급 수정과 되돌리기 (0.8.14부터)

출시한 버전에 문제가 생겼을 때 하는 일입니다. 푸시, 태그, 배포는 사장님이 바탕화면의 .cmd를 눌러서 합니다.
Claude는 커밋과 .cmd까지만 만듭니다.

## 0. 먼저 정할 것: 앱 문제인가, 서버 문제인가

| 증상 | 어디 | 가장 빠른 조치 |
|---|---|---|
| 앱이 켜지지 않음, 화면 오류, 부스트가 되돌려지지 않음 | 앱 | 1번(배포 멈추기) → 2번(긴급 수정) |
| 키 확인, 결제, 고객센터가 안 됨 | 서버 | 4번(서버 롤백) |
| 다운로드 페이지 문구나 링크가 틀림 | 사이트 | 5번(사이트 되돌리기) |

## 1. 문제 있는 릴리스의 배포 멈추기 (몇 분)

앱은 "정식(Latest) 릴리스"만 업데이트로 받고(`Services/Updater.cs`, prerelease = false), 다운로드 페이지도
`releases/latest/download/...`라서 정식 릴리스 중 가장 새것을 가리킵니다. 문제 있는 릴리스를 **시험판(pre-release)으로 바꾸면**
- 아직 업데이트하지 않은 사용자는 그 버전을 받지 않고,
- 다운로드 페이지는 바로 전 정식 릴리스를 내려줍니다.

```
gh release edit v0.8.15 --prerelease --repo DOKU-web/SystemBoost
gh release edit v0.8.15 --prerelease --repo DOKU-web/SystemBoost-releases   (새 저장소에도 올렸다면)
```

주의
- 이미 그 버전으로 업데이트한 사용자의 앱은 **자동으로 예전 버전으로 돌아가지 않습니다**. Velopack은 더 높은 버전으로만 업데이트합니다. 그래서 2번(더 높은 번호로 고친 버전)을 꼭 내야 합니다.
- 릴리스나 태그를 지우지 마세요. 지우면 델타 업데이트의 기준 파일이 사라집니다.

## 2. 긴급 수정 (고친 버전을 더 높은 번호로)

1. `C:\dev\SystemBoost-preview`에서 `hotfix/0.8.15` 같은 브랜치를 만들고 고칩니다.
   - 문제 커밋을 통째로 빼려면 `git revert <커밋>`(기록을 지우지 않고 되돌리는 새 커밋)을 씁니다. `reset --hard`나 강제 푸시는 쓰지 않습니다.
2. `app/SystemBoost.App/SystemBoost.App.csproj`의 `<Version>`을 올립니다(예: 0.8.14 → 0.8.15). 같은 번호나 낮은 번호는 사용자에게 가지 않습니다.
3. `RELEASE_NOTES.md` 맨 위에 새 버전 칸을 쓰고, 무엇을 고쳤는지 사용자 말로 적습니다.
4. 빌드와 시험
   - 앱: `dotnet build app\SystemBoost.App\SystemBoost.App.csproj -c Release` (오류 0)
   - 서버를 건드렸다면: `server/license-worker`에서 `node test_*.mjs` 전부
   - 바꾼 부분은 숨긴 데스크톱이나 새 Windows 사용자 계정에서 직접 확인합니다(실제 서버에 연결되니 결제는 하지 않습니다).
5. 브랜치를 preview에 합치고, Claude가 바탕화면에 `SystemBoost v0.8.15 배포.cmd`를 만듭니다.
   사장님이 누르면 main에 올리고 → GitHub에서 빌드와 테스트가 통과할 때만 → 태그를 올려 릴리스됩니다.
6. 릴리스가 올라오면 1번에서 시험판으로 바꾼 릴리스는 그대로 둡니다.

### "릴리스 되돌리기"가 필요할 때 (롤포워드)

예전 버전을 다시 올리는 방법은 없습니다(Velopack이 낮은 번호로는 업데이트하지 않습니다). 대신
**마지막으로 괜찮았던 코드를 더 높은 번호로 다시 냅니다.**

1. 1번으로 문제 버전의 배포를 멈춥니다.
2. `git switch -c revert/0.8.16 preview` 다음, 문제 버전에서 들어간 커밋을 `git revert`로 하나씩 되돌립니다
   (EULA나 서버와 맞물린 커밋은 함께 되돌려야 하는지 확인합니다).
3. 버전을 문제 버전보다 높게 올리고(예: 0.8.16), RELEASE_NOTES에 "0.8.15의 변경을 되돌렸어요"와 이유를 적습니다.
4. 2번의 4~5단계와 같습니다.

사용권 계약(`Eula.Version`)을 되돌릴 때는 주의하세요. 이미 동의를 받은 판을 낮추면 다시 동의를 묻지 않습니다.
계약 내용이 바뀌는 되돌리기는 제13조(30일 전 고지)를 다시 따라야 합니다.

## 3. 사용자에게 알리기

- 관리자 화면의 고객센터 공지(앱의 고객센터와 /help에 보임)에 짧게 씁니다: 무엇이 문제였는지, 사용자가 할 일(대개 "앱을 다시 켜면 고친 버전을 받아요").
- 관리자 화면의 Discord 공지로 같은 내용을 올립니다.
- 효과를 부풀리거나 원인을 추측해서 쓰지 않습니다.

## 4. 서버(Cloudflare Worker) 롤백

서버 코드는 배포할 때마다 버전이 남고, 이전 버전으로 되돌릴 수 있습니다.

```
cd C:\dev\SystemBoost-preview\server\license-worker
npx wrangler deployments list          # 최근 배포와 버전 ID
npx wrangler rollback <버전 ID> --message "이유"
```

- 되돌리는 것은 **코드뿐**입니다. KV에 이미 쓴 데이터(주문, 키, 고객센터 문의), Supabase의 데이터, Secret 값은 그대로입니다.
  새 코드가 데이터 모양을 바꿨다면, 예전 코드가 그 데이터를 읽을 수 있는지 먼저 확인합니다.
- Durable Object(통계)의 migration을 바꾼 배포는 롤백으로 되돌아가지 않을 수 있습니다. 이런 배포는 미리 표시해 둡니다.
- 롤백한 다음에는 고친 코드를 2번처럼 시험한 뒤 다시 배포합니다.
- 이 명령은 실제 운영 서버를 바꿉니다. Claude는 실행하지 않고, 필요하면 바탕화면 .cmd로 만듭니다.
- 확인 상태: 위 명령은 Wrangler 문서의 명령 이름을 따랐고, 이 계정에서 실제로 롤백해 보지는 않았습니다(미검증).

## 5. 다운로드 사이트 되돌리기

사이트는 gh-pages 브랜치의 `index.html` 하나입니다(2026-11 기준. 새 저장소로 옮긴 뒤에는 그 저장소의 Pages).

```
git log --oneline origin/gh-pages      # 되돌릴 커밋 찾기
git revert <커밋>                       # gh-pages 브랜치에서
```

푸시는 사장님이 .cmd로 합니다. GitHub Pages는 보통 몇 분 안에 바뀝니다.
