# 회원 계정 v2 보안 시험 (2026-11-17)

메일 가입, 비밀번호 재설정, 2단계 인증(TOTP와 백업 코드), 기기, 키 연결, 계정 복구 요청을 이 PC에서만 시험했습니다.
실제 Supabase, Cloudflare, Resend에는 연결하지 않았고 메일은 한 통도 보내지 않았습니다(가짜 Resend가 기록만 합니다).

## 방법

- 손으로 하는 공격: `node docs/account_attacks.mjs 40`. Worker(`src/index.js`)를 같은 프로세스에서 부르고, 회원 DB는
  PGlite(실제 Postgres를 WebAssembly로 돌린 것)에 `supabase/accounts.sql`을 그대로 올린 것, 통계 저장소는 `fake_stats.mjs`,
  메일은 기록만 하는 가짜 Resend입니다. 무엇도 단언하지 않고 공격자가 받는 답을 그대로 찍습니다.
- 자동 시험: `test_accounts_security.mjs` 11번 묶음(9개)과 `test_accounts_email.mjs`. 아래 '자동 시험' 참고.
- 시간은 요청을 보낸 뒤 답을 받을 때까지(메일은 답 뒤에 보내므로 들어가지 않습니다). 계정이 있는 경우와 없는 경우를 번갈아 40번씩 쟀습니다.

### 2. 2단계 코드 추측 (비밀번호를 아는 공격자)

| 시도 | 결과 |
|---|---|
| 대기 중 로그인에 틀린 코드 12번 | 401 `wrong` 5번, 그 뒤 400 `expired` 7번 |
| 그 뒤 새 로그인 | 429 `locked` (계정이 15분 잠김) |
| 한 대기 로그인에 백업 코드 6번 | 401 `wrong` 5번, 400 `expired` 1번 (대기 로그인은 5번 틀리면 사라짐) |

6자리 코드는 ±1 단계(앞뒤 30초)까지 받으므로 한 번 맞힐 확률은 3/1,000,000이고, 5번 틀리면 15분 잠깁니다.
한 번 쓴 코드와 그보다 오래된 단계의 코드는 다시 받지 않습니다.

## 자동 시험

- `test_accounts_security.mjs` 38개 모두 통과. 11번 묶음(계정 v2):
  - 없는 아이디 · 메일도 5번 틀리면 같은 답으로 잠김
  - 한 IP: 로그인 20번, 메일 가입 5번, 비밀번호 찾기 · 키 다시 받기 · 복구 요청 10번(한 시간)
  - 가입, 비밀번호 찾기, 키 다시 받기, 복구 요청: 계정이 있든 없든 같은 답, 같은 쓰기
  - 메일 링크: 한 번만, 자기 종류에만, 재설정은 가장 새 것만, 30분
  - 2단계: 코드와 백업 코드는 한 번만, 자기 계정에만, 대기 로그인 바꿔치기 안 됨
  - 기기: 남의 기기 번호로는 아무것도 끝나지 않음, 재설정과 '모든 기기 로그아웃'은 세션을 끝냄
  - 키 연결 링크는 키의 구매 메일로만 가고, 요청한 계정에만 연결됨
  - IP 주소를 그대로 두는 곳은 보안 기록뿐, 메일 · 코드 · 링크는 어디에도 그대로 없음
  - 옛 DB에 새 Worker: 지금 동작은 그대로, 새 동작은 503 `unavailable`, 유효한 토큰에 `session`을 답하지 않음
  - Worker의 로그와 오류 답에 메일, 링크, 코드, IP 주소가 없음
  - 10번(마이그레이션): af5b464의 DB에 `supabase/migrations/20261118_email_accounts.sql`을 두 번 실행해도 회원, 비밀번호, 복구 코드, 세션이 그대로이고,
    표 · 열 · 색인 · 권한이 `accounts.sql`로 새로 만든 DB와 같음
- `test_accounts_email.mjs`: 비밀번호 규칙, `features`와 `mail_off`, 메일 가입과 확인 페이지, 동의 판, 로그인과 기기, 2단계 인증,
  비밀번호 찾기와 재설정, 메일 추가, 키와 키 연결과 키 다시 받기, 동의 기록, 계정 복구(대기, 취소, 승인, 거절), 탈퇴, 메일 상한, 로그에 비밀 없음.

## 코드 검토 (2026-11-18, 통합 브랜치 feat/accounts)

다른 에이전트가 코드를 읽고 PGlite와 가짜 객체로 재현했습니다(네트워크 없음). 고친 것은 test_accounts_email.mjs 끝의 'review 2026-11-18'에서 확인합니다.

- 고침: 2단계 인증을 켠 아이디 계정이 복구 코드만으로 비밀번호를 바꾸고 세션을 받던 것. 이제 `recover`는 403 `twofa`로 거절하고, 계정 복구 요청을 쓰게 합니다.
- 고침: 메일로 비밀번호를 재설정해도 전에 받은 복구 코드가 계속 쓰이던 것. 재설정하면 복구 코드를 무효로 합니다(앱에서 비밀번호를 바꾸면 새 코드를 받아요).
- 고침: 계정 복구를 승인해도 예전 비밀번호로 로그인되던 것. 승인하면 비밀번호를 무효로 하고, 메일 계정은 복구 코드도 무효로 합니다.
- 고침: 다른 사람이 먼저 같은 메일로 가입해 둔 링크를 주인이 누르면 그 사람의 비밀번호로 계정이 만들어지던 것. 가입 확인 페이지는 앱에서 정한 비밀번호를 함께 묻고, 다섯 번 틀리면 링크가 끝납니다. 메일 주소 연결 메일에는 아이디를 적었습니다.
- 고침: 아무 주소로나 가입해서 하루 메일 한도를 다 쓰게 할 수 있던 것. 가입 확인 메일은 하루 한도의 절반까지만 씁니다.
- 남김(낮음): 아이디로 5번 틀려 잠근 뒤 그 계정의 메일로 로그인하면 'locked'가 나와서, 아이디와 메일이 같은 계정인지 알 수 있습니다. 5번 틀리게 해야 하고 그 계정이 15분 잠깁니다.
- 남김(낮음): 누구나 아무 계정에 복구 요청을 먼저 넣어 두면, 주인의 요청은 조용히 무시됩니다(열린 요청은 계정마다 하나). 메일 계정은 첫 요청의 취소 링크를 메일로 받고, 판매자는 결제 정보가 맞지 않는 요청을 거절합니다.

## 미검증

- 실제 Supabase(PostgREST 경유)와 실제 네트워크에서의 시간 차이. 위 숫자는 같은 프로세스 안의 PGlite 기준입니다.
  실제로는 네트워크 흔들림이 훨씬 커서 차이가 더 묻히겠지만 재지 않았습니다.
- 실제 Resend API: 보내기, 도착률(스팸함), 메일 앱에서 보이는 모양, 보내는 도메인의 DNS(SPF, DKIM).
- 메일 보안 검사기(회사 메일 등)가 링크를 미리 여는 경우: 페이지는 GET에서 아무것도 하지 않고 POST(버튼)에서만 처리하도록 만들었지만,
  실제 검사기로는 시험하지 않았습니다.
- Cloudflare의 로그 기능을 켜면 요청 주소에 들어 있는 링크 토큰(`?t=`)이 로그에 남을 수 있습니다. 토큰은 한 번만 쓰고 짧게 끝나지만 확인하지 않았습니다.
- `request.cf.country`(실제 Cloudflare에서만 채워짐), 실제 Workers의 CPU 시간(무료 플랜 10 ms. TOTP, AES-GCM, HKDF는 Web Crypto라 가볍다고 봤지만 재지 않았습니다).
- IPv6 주소를 /64로 묶는 것은 단위 시험만 했고 실제 IPv6 요청으로는 시험하지 않았습니다.
- 대시보드 '복구 요청' 화면을 실제 브라우저에서 열어 보지 않았습니다(스크립트 문법과 시연 모드 데이터만 확인).
- 앱 쪽(로그인 화면, 2단계 인증, 기기 목록, 동의 기록 보내기)은 이 작업 범위가 아니라 시험하지 않았습니다.
- 2단계 인증 잠금은 비밀번호를 아는 사람이 일부러 계정을 15분씩 잠글 수 있게 합니다. 비밀번호를 아는 사람만 할 수 있어서 그대로 두었습니다.
