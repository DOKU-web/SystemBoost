# 라이선스 서버 + 관리자 대시보드

Cloudflare Workers + KV (무료 플랜으로 충분). 결제는 판매자가 직접 받고(본인 결제 페이지 링크),
결제를 확인한 뒤 대시보드에서 키를 발급하면 구매자 앱에 팝업으로 뜹니다.

결제 방식은 두 가지이고 함께 켤 수 있습니다. 둘 다 열려 있으면 구매자가 앱에서 '카드 결제'와 '계좌이체 · 직접 결제' 중에 고릅니다.

**계좌이체 · 직접 결제**: 대시보드에 결제 링크를 넣으면 켜짐. 사장님이 확인하고 승인
```
앱 '결제하기' → 주문 코드 SB-XXXX-XXXX + 결제 링크 열림                       [신청 중]
구매자: 결제 메모에 코드 → 앱에서 입금자명 적고 '결제했어요'                  [결제 확인 요청]
사장님: 대시보드 '결제 신청'에서 확인 → '승인'(키가 무작위로 생성돼 앱에 팝업) [승인]
                                    또는 '거절'(사유가 구매자 앱에 표시)       [거절]
```
**카드 결제 (Lemon Squeezy)**: 대시보드 '카드 결제'를 테스트/실판매로 켜면 열림. 결제가 확인되면 사람 손 없이 키 생성·자동 승인.
월간·연간은 카드가 등록되는 구독이라 기간마다 자동 결제되고, 앱이 만료 7일 전에 새 키를 받아 와 자동 연장합니다.
카드 정보는 Lemon Squeezy 결제창에서만 입력돼요. SystemBoost 앱과 서버에는 카드 정보가 오지도, 저장되지도 않습니다.
```
앱 '결제하기' → 주문 코드를 실은 Lemon Squeezy 결제창 → 결제 → 서명 확인된 웹훅
→ 키 자동 생성 → 주문 [승인] (기록에 '자동 승인') → 앱 팝업
```
앱은 키가 나올 때까지 기다립니다(처음 15분은 5초마다, 그 뒤 1분마다, 앱을 껐다 켜도 14일까지).
키는 매번 새로 만들어지고 서명돼서 같은 키가 두 번 나오지 않습니다.

**결제 준비 전에는 키가 나가지 않습니다.**
- 자동 승인은 결제 업체가 서명한 결제 확인(웹훅)이 올 때만 일어납니다. 수동 확인 방식에서 자동 승인은 없습니다
  (구매자의 '결제했어요'만으로 키를 주면 결제 없이도 키를 받을 수 있기 때문).
- 대시보드에 결제 링크가 없는 플랜은 앱에서 '결제 준비 중'으로 잠기고, 서버도 주문을 만들지 않습니다(503).
- 키는 판매자가 대시보드에서 '키 발급'을 누를 때만 만들어집니다.
- 자동 결제(Lemon Squeezy 웹훅) 경로의 판매 모드 기본값은 `off`: 웹훅이 와도 키를 만들지 않습니다.

## 관리자 대시보드 (`https://<서버 주소>/admin`)
| 기능 | 설명 |
|---|---|
| 실시간 사용 현황 | 지금 켜져 있는 앱, 오늘·7일·30일 사용자, 누적 설치, 켜 둔 시간, 프레임 생성 사용. 15초마다 갱신 |
| 다운로드 | GitHub 릴리스 집계: 설치 파일 전체, 오늘, 파일 종류별, 버전별 |
| 최근 30일 · 사용자 구성 | 일별 사용자 · 새 설치 · 다운로드, 플랜 · 운영체제 · 버전 · 국가 |
| 요약 | 사용 중 · 최근 30일 발급 · 만료 · 차단 · 전체 키 수 |
| 결제 방식 | 계좌이체 · 직접 결제(결제 링크가 있으면 켜짐) + 카드 결제(꺼짐 / 테스트 / 실판매) |
| 결제 신청 | 처리할 것(신청 중 · 결제 확인 요청) / 승인 / 거절 / 전체. 입금자명·메모를 보고 승인 또는 거절(사유 입력) |
| 키 발급 | 월간(34일) · 연간(369일) · 직접 입력(일). 주문 코드가 있으면 구매자 앱에 바로 뜨고, 없으면(선물·리뷰용) 키를 복사해 보내면 됨 |
| 결제 링크 | 플랜별 https 링크(프리미엄 3개, 울트라 3개). 비우면 그 플랜은 앱에서 잠김. 앱은 프리미엄 화면을 열 때 반영. 카드 결제(Lemon Squeezy)는 프리미엄만 |
| 키 직접 발급 | 기간을 고르고 '프리미엄 키 발급' 또는 '울트라 키 발급'을 누름. 울트라는 프레임 생성 6·8배, 듀얼 GPU, 게임별 자동 최적화, GPU 오버클럭까지 열림. 앱에서 받은 주문을 승인하면 주문한 플랜의 키가 나감 |
| 발급된 키 | 메일 · 키 번호 · 주문 코드 · 메모로 검색, 상태별 보기, 키 다시 복사, 차단/해제 |
| 키 확인 | 구매자가 보낸 키를 붙여 넣으면 서명이 진짜인지, 차단됐는지, 언제 발급·만료인지 보여 줌 |
| 기록 | 발급 · 차단 · 링크 변경 등 최근 100개 (180일 보관) |
| 디스코드 공지 | 채널·알림을 고르고 글을 써서 미리 본 뒤 보내기. 템플릿, 보낸 글 수정·삭제(최근 50개). 아래 '디스코드 공지' 참고 |
| 고객센터 | 문의 목록(처리할 것 · 답변함 · 닫힘 · 환불 · 전체), 답장, 환불 승인 · 거절 · 완료, 설정. 맨 위 '새 소식'에 구매자가 한 일이 새로고침 없이 뜸(탭이 보일 때 30초마다). 아래 '고객센터 · 환불' 참고 |

**차단**은 앱이 인터넷에 연결된 상태로 켜질 때 적용돼요(`/check`). 오프라인 PC는 다음 연결 때까지 그대로 동작합니다.
구독 키를 차단하면 갱신도 멈춥니다. 자동 결제 환불(`order_refunded`)은 해당 키를 자동으로 차단합니다.

보안
- 대시보드는 `ADMIN_TOKEN`이 없거나 6자보다 짧으면 꺼져 있습니다(404).
- 비밀번호를 틀리면 잠깁니다: 같은 IP에서 5번 틀리면 15분, 전체 합쳐 한 시간에 20번 틀리면 그 시간 동안 잠김.
  6자리 숫자(100만 가지)를 한 시간에 20번씩 대입하면 수천 년이 걸려요. 대신 누가 일부러 틀려서
  잠깐 잠그게 만들 수는 있어요. 그럴 땐 기다리거나 `wrangler secret put ADMIN_TOKEN`으로 비밀번호를 바꾸세요.
- 비밀번호는 브라우저 탭 안(sessionStorage)에만 있고 탭을 닫으면 지워집니다. 페이지에 비밀 값은 들어 있지 않습니다.
- 관리자 API는 다른 사이트에서 호출할 수 없게(CORS 없음) 했고, 페이지는 CSP로 외부 스크립트를 막습니다.
- 더 막고 싶다면 Cloudflare Zero Trust Access로 `/admin*` 경로에 본인 메일 로그인을 추가하세요(무료 50명).

## 디스코드 공지 (`src/announce.js`)
대시보드 맨 아래, 또는 위쪽 '디스코드 공지' 버튼으로 갑니다.

- 웹후크 주소가 있으면 누구나 그 채널에 글을 올릴 수 있고, 이 저장소와 대시보드 페이지는 공개입니다. 그래서 주소는 코드에 넣지 않습니다.
- 대시보드 '디스코드 연결'에서 주소를 넣으면 KV `config:discord_hooks`에 저장됩니다. 저장한 뒤에는 어떤 응답과 기록에도 나오지 않고, 디스코드 호출은 전부 서버가 합니다.
- 저장할 때 웹후크를 읽어서 살아 있는지, 맞는 채널인지 확인합니다. 이때 글은 올라가지 않습니다.
- 보낸 글 목록은 KV `announce:hist`에 최근 50개까지 있습니다. 수정·삭제는 이 목록의 글만 됩니다. 웹후크를 새로 만들면 예전 웹후크로 보낸 글은 수정·삭제할 수 없습니다.
- 채널과 역할을 바꾸려면 `src/announce.js`의 `CHANNELS`, `ROLES`를 고칩니다.
- Workers 주소는 다른 사이트와 함께 쓰여서 디스코드가 잠시 막을 수 있습니다. 그때는 화면에 그렇게 나오고, 글은 올라가지 않습니다.

## 회원 (`src/accounts.js`, `supabase/accounts.sql`)
앱의 '계정' 화면에서 가입합니다. 회원이 아니어도 앱은 그대로 쓸 수 있습니다.
- 회원 정보는 Supabase(무료 플랜)의 Postgres에 있습니다. 앱은 이 Worker만 부르고, Worker만 비밀 키로 Supabase에 갑니다. 키, 추천 코드, 통계는 Cloudflare에 그대로 있습니다.
- 처음 한 번: Supabase SQL Editor에서 `supabase/accounts.sql` 전체를 실행하고, `wrangler secret put SUPABASE_URL`, `wrangler secret put SUPABASE_SECRET_KEY`를 넣습니다.
- 공개 키(publishable)로는 표도 함수도 닿지 않습니다. SQL 끝에서 이것을 확인하고, 다르면 오류로 멈춥니다.
- 아이디와 비밀번호로 가입합니다. 메일은 받지 않습니다. 가입할 때 복구 코드를 한 번 보여 주고, 비밀번호를 잊으면 그 코드로 바꿉니다.
- 비밀번호는 Worker에서 섞는 값(pepper)과 합친 뒤 DB에서 bcrypt로 저장합니다. 섞는 값은 서명 키에서 만들기 때문에 서명 키를 바꾸면 모든 비밀번호와 복구 코드가 끝납니다.
- 가입에는 개인정보 수집·이용 동의와 만 14세 이상 확인이 필요합니다. 동의한 시각을 저장합니다.
- 초대 코드: 회원이 앱에서 만듭니다. 그 코드로 가입한 사람은 프리미엄 3일을 받고, 초대한 회원은 한 명당 3일을 쌓아 앱에서 키로 받습니다(모두 30일까지, 코드당 50명). 숫자는 `src/accounts.js`의 `LIMITS`에 있습니다.
- 할인 티켓: 가입할 때 초대 코드를 쓴 회원은 10% 티켓을 받습니다(30일, 1회). 직접 결제 링크는 금액이 고정이라, 대시보드의 '할인 티켓' 링크(정가의 90%)로 보냅니다. 주문을 승인하면 쓴 것으로 처리하고, 거절하거나 지우면 돌려줍니다. 카드 결제에는 쓸 수 없습니다.
- 대시보드 '회원'에서 찾기, 차단, 복구 코드 재발급, 삭제를 합니다.
- 무료 플랜은 활동이 없으면 프로젝트가 일시 중지되고 백업이 없습니다. 매시간 작업이 Supabase를 한 번 부르지만, 어떤 활동을 인정하는지는 공개되어 있지 않습니다. 중지되면 Supabase 화면에서 복구합니다. 그동안 회원 기능만 멈추고 키 확인은 그대로 됩니다.
- 테스트: `npm i --no-save @electric-sql/pglite` 후 `node test_accounts.mjs`

## 추천 코드
대시보드 '추천 코드'에서 만듭니다. 코드, 메모, 플랜, 기간(1~30일), 사용 횟수 한도를 정하고 켜고 끌 수 있습니다.
- 앱의 프리미엄 화면에서 코드를 입력하면 `POST /referral`로 서명된 키를 바로 받습니다. 키는 키 목록에 메모 `추천 코드 <코드>`로 남습니다.
- 한 기기는 코드 하나만 한 번 씁니다(`refdev:<기기 번호>`, 90일 뒤 삭제). 기기 번호는 앱이 만든 무작위 값이라, 앱 데이터를 지우면 다시 쓸 수 있습니다. 코드별 한도와 하루 300개 상한이 그 위를 막습니다.
- 유료 키가 켜져 있으면 앱이 코드를 받지 않습니다. 짧은 키로 덮어쓰지 않기 위해서입니다.
- 코드를 나눠 준 사람의 보상은 자동이 아닙니다. 사용 횟수를 보고 직접 키를 발급합니다.
- 테스트: `node test_referral.mjs <임시 pem>`

## 사용 통계 (`src/stats.js`)
- 앱은 동의 후 `POST /ping`으로 무작위 설치 번호, 버전, 운영체제, 플랜, 프레임 생성 배수, 원클릭 부스트 여부를 보냅니다. 끌 수 있고, 무엇을 보내는지는 사용권 계약 제8조에 적혀 있습니다. 보내는 항목을 바꾸면 계약 문구도 함께 고치고 `Eula.Version`을 올려야 합니다.
- 저장 위치는 Durable Object(SQLite)입니다. 신호마다 쓰기가 생기는데 KV 무료 플랜은 하루 1,000번까지만 쓸 수 있어서입니다. `wrangler deploy`가 알아서 만듭니다.
- 신호 간격은 서버가 정합니다(그날 사용자 100명 미만 60초, 400명 미만 5분, 1,500명 미만 15분, 그 이상 1시간). Workers 무료 플랜은 하루 10만 요청을 넘으면 라이선스 확인과 주문까지 멈추기 때문입니다.
- 설치 번호는 마지막 연결 뒤 90일이 지나면 지워지고, 날짜별 합계는 남습니다. IP 주소는 저장하지 않습니다.
- 같은 Durable Object에 고객센터 '새 소식' 표(`support_events`)도 있습니다. 아래 '고객센터 · 환불'을 보세요.
- 다운로드는 GitHub 릴리스 파일의 누적 횟수입니다. 매시간 cron과 대시보드가 가져오고, GitHub이 Workers 주소를 거부하면 대시보드를 연 브라우저가 대신 가져옵니다. `releases.*.json`과 `RELEASES`는 업데이트 확인마다 읽히므로 세지 않습니다.
- 숫자는 가짜 신호로 부풀 수 있습니다. 인증 없는 공개 주소라서입니다. 새 설치는 하루 3,000개에서 막습니다.
- 로직 시험: `node test_stats.mjs`. 실제 런타임 시험: `wrangler dev --local --test-scheduled`.

## 고객센터 · 환불 (`src/support.js`, `src/help_page.js`)
앱의 '고객센터'와 웹 페이지 `https://<서버 주소>/help`(영어는 `?lang=en`)에서 문의를 받습니다. 판매자는 대시보드에서 답하고 환불을 처리합니다.

주소 (공개)
- `GET /support/info`: 판매자 정보, 공지, 자주 묻는 질문, 문의 종류, 환불 사유, 제9조(`?lang=en`).
- `POST /support/ticket`: 새 문의 → `{id, token}`. 확인 코드(`token`)는 이때 한 번만 보여 줍니다.
  키는 `key`(키 전체)나 `keyId`(키 식별 번호, 16자리)로 받습니다. `key`는 서명을 확인한 뒤 키 식별 번호와 `keyVerified: true`만 남기고, 키 자체는 저장하지도, 로그에 남기지도, 돌려주지도 않습니다. 서명이 틀리면 400 `bad key`, `key`와 다른 `keyId`를 함께 보내면 400 `keyId`입니다. `keyId`만 보내면 `keyVerified: false`입니다.
- `GET /support/ticket?id=<번호>`: 문의 보기. 확인 코드는 헤더 `X-Ticket-Token`으로 보냅니다.
- `POST /support/ticket/reply` `{id, token, text}`, `POST /support/ticket/close` `{id, token}`.
- `POST /support/tickets/status`: 앱의 답장 확인(아래).
- `POST /support/subscription` `{key}`: 카드 구독의 고객 포털 링크(아래).
- 확인 코드는 URL에 넣지 않습니다. `/support` 아래 어느 주소든 쿼리에 `token`이 있으면 400 `token in url`입니다. URL은 접속 기록과 방문 기록에 남기 때문입니다.
- 없는 문의와 틀린(또는 빠진) 확인 코드는 똑같은 404 `not found`입니다.
- 요청 본문이 64KB를 넘으면 413 `too large`입니다. `Content-Length`가 크면 읽지 않고, 읽다가 넘으면 거기서 멈춥니다. 너무 긴 글은 정리하기 전에 거절합니다.

저장하는 것 (KV `tk:<문의 번호>`)
- 문의 종류, 제목, 내용과 답변(문의 하나에 30개까지), 시각, 보관 안내에 동의한 시각.
- 구매자가 적은 연락처, 주문 코드, 키 식별 번호. 키 식별 번호는 키가 아니라 키의 SHA-256 앞 16자리입니다. 구매자가 키 전체를 보내면 서버가 서명을 확인하고 키 식별 번호만 남깁니다(`keyVerified: true`). /help도 키 전체를 그대로 서버에 보내고, 서버는 키를 저장하지 않습니다.
- 앱에서 '앱 정보 함께 보내기'를 고르면 앱 버전, 운영체제, GPU 이름.
- 회원으로 로그인한 앱에서 보내면 회원 아이디.
- 환불 요청이면 서버가 아는 키와 주문 정보: 플랜, 발급일, 만료일, 결제 방식, 입금자명, 주문 상태, 키를 받은 지 며칠. 서버가 그 주문을 찾았으면 `orderMatched: true`.
- 구매자가 받는 확인 코드는 저장하지 않습니다. 해시만 저장하고, 코드는 보낼 때 한 번만 보여 줍니다. 코드를 잃으면 구매자는 그 문의를 다시 열 수 없습니다. 판매자는 대시보드에서 계속 봅니다.
- IP 주소는 저장하지 않습니다. 횟수 제한에는 SHA-256(IP + "sb-support")의 앞 16자리를 씁니다. 이 값은 Cloudflare 캐시(Cache API)에 1시간, 서버 메모리에는 그 시간이 끝난 뒤 1분 안에 지워질 때까지 있습니다. 해시라서 바로 읽히지는 않지만, IPv4 주소는 모두 해시해 볼 수 있으니 되돌릴 수 없다고 하지 않습니다. IPv6는 앞 64비트(/64)로 묶어 셉니다. 한 집이나 한 휴대폰 망이 주소를 바꿔 가며 보내도 한 곳으로 셉니다.

보관 기간
- 결제 · 환불 문의는 3년, 그 밖의 문의는 1년입니다. 문의가 바뀔 때마다(글, 답장, 상태, 새 답장을 읽음) 처음부터 다시 셉니다.
- 기간이 지나면 KV가 지웁니다. 대시보드에서 바로 지울 수도 있습니다.

제한
- 같은 IP에서 한 시간에: 새 문의 5개, 답장 20개, 답장 확인 120번, 구독 관리 링크 20번. 넘으면 429 `{"error":"busy","scope":"ip"}`, `Retry-After`는 그 시간이 끝날 때까지의 초입니다(예산 열쇠에 쓰다 실패해 다시 보내야 할 때는 2초).
- 하루 예산은 두 칸입니다. 넘으면 그 칸의 쓰기만 429 `{"error":"busy","scope":"day"}`, `Retry-After`는 다음 UTC 0시(한국 시간 오전 9시)까지의 초입니다.

  | 칸 | 누구 | KV 쓰기 | 새 문의 | 구매자 답장 |
  |---|---|---|---|---|
  | 익명 | 아래가 아닌 모든 문의 | 250번 | 80개 | 80개 |
  | 구매 확인 | 서명된 키 전체를 보낸 문의, 승인되었거나 환불된 주문의 코드를 적은 문의 | 150번 | 40개 | 60개 |

  구매 확인 칸은 구매 하나(키 식별 번호나 주문 코드)마다 하루 20번까지입니다. 그래서 익명 문의가 하루 칸을 다 채워도 산 사람은 문의할 수 있고, 구매 하나가 그 칸을 다 쓰지 못합니다. 주문 신청만 한 코드와 키 식별 번호만 적은 문의는 누구나 만들 수 있어 익명 칸입니다.
- 하루 예산은 KV 열쇠 하나(`count:support:<날짜>`, `{w,c,r}`와 구매 확인 칸의 `{vw,vc,vr,by}`, 2일 보관)에 셉니다. 쓰는 문의 동작마다 먼저 자기 칸을 확인하고, 그 열쇠에 쓰는 것까지 셉니다.
- 하루 KV 쓰기의 최악: 고객센터는 250 + 150 = 400번을 넘지 않습니다. 익명으로 채울 수 있는 것은 250번이고, 나머지 150번은 실제 구매가 8개 넘게 있어야 채웁니다(구매 하나에 20번). 여기에 '안 읽음' 지우기가 판매자 답장 수만큼 더해집니다(아래). 무료 플랜의 쓰기는 하루 1,000번이니 다른 일에 600번이 남습니다. 주문 신청(/order)은 하루 300개(주문 하나에 2번, 결제 확인 요청까지 3번)로 막혀 있습니다. 공격자가 같은 날 고객센터 익명 칸(250번)과 주문 신청(최대 900번)을 함께 다 채우면 1,150번으로 무료 플랜을 넘을 수 있습니다. 그런 날에는 그 뒤의 KV 쓰기(키 발급 포함)가 실패하니, 그런 일이 생기면 유료 플랜이나 주문 한도를 다시 봐야 합니다.
  주문, 결제 확인, 키 발급과 /claim, 웹훅, 대시보드는 고객센터 예산과 상관없이 그대로 됩니다.
- IP별 횟수는 KV에 쓰지 않습니다. Cloudflare 캐시(Cache API)와 서버 메모리에 1시간 둡니다. 둘 다 지역(데이터센터)마다 따로라 대략적인 수입니다.
  지금 주소(`*.workers.dev`)에서는 Cloudflare가 Cache API 동작을 약속하지 않습니다. 그때는 메모리만 세서 IP별 제한이 느슨해지고, 하루 예산이 막습니다.
- KV 쓰기: 새 문의 2번, 환불 요청은 키를 보여 준 경우(서명된 키, 또는 서버가 찾은 주문의 키)만 3번(웹훅이 찾는 `tkkey:<키 식별 번호>`), 답장 2번, 닫기 2번. 예산 열쇠에 쓰는 1번이 들어 있습니다.
- 새 답장을 읽으면 '안 읽음' 표시를 지우느라 1번 씁니다. 판매자 답장만 이 표시를 켜므로 예산에 세지 않고, 그 문의의 칸을 다 쓴 날에는 KV에서 지우지 않고 둡니다. 그때는 '본 표시'를 캐시와 메모리에 두어(대략적) 같은 답장을 다시 새 답장으로 알리지 않습니다. 다음 날 읽으면 지웁니다.
- 제목 80자, 내용 2,000자, 연락처 120자, 문의 하나에 메시지 30개. 글자 수는 서버와 /help가 똑같이 셉니다(이모지 하나도 한 글자).
- 닫은 문의는 닫은 뒤 30일 안에 구매자가 답장하면 다시 열립니다. 그 뒤에는 새 문의를 씁니다.
- 대시보드에서 문의를 닫아 두면(문의 받기 끄기) 새 문의만 막히고, 이미 있는 문의의 답장은 됩니다.
- `/support` 아래 POST는 `Content-Type`이 `application/json`일 때만 받습니다(`; charset=utf-8` 같은 덧붙임과 대소문자는 상관없음). 아니면 415입니다.
  다른 사이트의 페이지는 브라우저가 미리 묻지 않고는 JSON을 보낼 수 없고, 서버는 그 물음(OPTIONS)에 답하지 않습니다. 그래서 다른 사이트가 방문자 몰래 문의를 넣지 못합니다. 앱과 /help는 JSON으로 보냅니다. /order 같은 다른 주소는 전과 같습니다.

답장 확인 (`POST /support/tickets/status`): 앱이 문의 여러 개의 새 소식을 한 번에 묻습니다.
- 보내는 것: `{"tickets":[{"id":"T-…","token":"<확인 코드>"}]}`, 한 번에 1~20개. 형식이 틀리면 400 `tickets`.
- 받는 것: `{"tickets":{"<번호>":{"status","updated","n","unread"}}}`. `n`은 메시지 수입니다. 없는 번호와 틀린 확인 코드는 똑같이 `null`입니다.
- 읽기만 합니다. KV에 쓰지 않고 '안 읽음'도 그대로 둡니다. 지우는 것은 문의를 열어 볼 때(`GET /support/ticket`)입니다. 구매자가 이미 본 답장(위의 '본 표시')은 `unread: false`입니다.
- KV 읽기는 문의 하나에 1번입니다(같은 번호가 여러 번이면 1번, 확인 코드 형식이 아니면 0번). 한 IP가 한도까지 부르면 한 시간에 2,400번까지 읽습니다. 무료 플랜의 읽기는 하루 100,000번입니다.

환불. 돈은 이 서버를 지나가지 않습니다. 판매자가 정하고, 판매자가 돌려줍니다.
- 앱과 /help는 사용권 계약 제9조를 그대로 보여 줍니다. 환불이 되는지는 판매자가 판단합니다. 서버와 앱은 판단하지 않습니다.
- 환불 요청에는 서버가 아는 사실이 붙습니다. 구매자가 쓴 내용과 맞는지는 판매자가 봅니다.
- 구매자 화면(앱, /help)에는 그 사실 중 플랜, 발급일, 받은 지 며칠만, 그것도 키 소유를 보였을 때(`keyVerified`)나 서버가 주문을 찾았을 때(`orderMatched`)만 보입니다. 키 식별 번호는 키를 본 적 있는 누구나 적을 수 있어서, 번호만 적은 사람에게는 아무 사실도 보여 주지 않습니다.
- 대시보드는 사실을 모두 보여 주고, 번호만 적은 요청에는 "키 소유 확인 안 됨: 구매자가 키 식별 번호만 적었어요"를 붙입니다. 그런 키를 막는 '환불 완료'는 한 번 더 확인해야 합니다(API: `"confirmUnverified": true`, 없으면 409와 그 키 목록).
- 승인, 거절: 대시보드에서 누르면 구매자에게 메시지가 갑니다. 거절에는 사유가 필요하고, 사유는 구매자에게 보입니다.
- 카드 결제(Lemon Squeezy): 판매자가 Lemon Squeezy 대시보드에서 환불하고, 구독이면 구독도 해지합니다. 환불 웹훅이 키를 막고, 그 키를 보여 준 환불 요청을 '환불 완료'로 바꾸고, 주문을 '환불'로 표시합니다.
- 계좌이체 · 직접 결제: 판매자가 직접 돌려준 뒤 대시보드에서 '환불 완료'를 누릅니다. 그 주문의 키를 모두 막고(묶음이면 묶음 키 전부), 주문을 '환불'로 표시합니다. 키를 남기려면 키를 막지 않게 하고 누릅니다.
- '환불'로 표시하는 주문은 승인된(결제가 확인된) 주문뿐입니다. 막을 키도 없고 승인된 주문도 아니면 '환불 완료'는 409로 거절됩니다. 주문 코드와 키를 확인하세요.
- 환불을 마치면 그 주문의 `session:`과 `bundle:`을 지웁니다. 앱이 /claim으로 그 키를 다시 받아 가지 못합니다. 환불한 주문의 코드로 키를 다시 발급(`POST /admin/api/issue`)하면 409입니다. 다시 팔았다면 새 주문 코드로, 또는 주문 코드 없이 메모를 적어 발급합니다.
- 막은 키는 앱이 인터넷에 연결된 상태로 켜질 때 무료 플랜으로 돌아갑니다.

주문 코드와 키가 서로 다른 구매일 때(예: 앱이 기다리던 새 주문 코드와 이 PC의 예전 키를 함께 보냄)
- 주문 코드가 요청의 대상입니다. 플랜, 발급일, '키를 받은 지 며칠'은 그 주문의 키로 셉니다. 주문에 아직 키가 없으면 비워 둡니다.
- 구매자가 적은 키는 `facts.otherKeyId`(그 키의 주문은 `facts.otherOrder`)로 따로 두고 `facts.mismatch = true`를 붙입니다. 대시보드는 빨간 경고와 두 구매의 키를 함께 보여 줍니다.
- 이 요청의 '환불 완료'는 그 다른 키를 막지 않습니다. 그 키의 환불 웹훅도 이 요청을 닫지 않습니다. 다른 구매도 환불한다면 그 구매로 따로 처리합니다.
- 키만 적은 요청은 키 메모의 주문 코드로 주문을 찾습니다. 주문 기록이 지워진 뒤(90일)에도 그 코드의 키를 모두 찾습니다.
- 주문 코드도 키도 서버에 없으면 비교할 것이 없어 경고를 붙이지 않습니다.

자동으로 되지 않는 것
- 환불할지 정하는 일, 돈을 돌려주는 일, 카드 구독 해지.
- '환불 완료'는 Lemon Squeezy 구독을 해지하지 않습니다. 키를 막으면 갱신 키는 더 나가지 않지만, 카드 결제는 Lemon Squeezy에서 해지할 때까지 계속됩니다.
- 웹훅은 막은 키와 요청의 키가 같고, 구매자가 그 키를 보여 준 요청(서명된 키, 또는 서버가 찾은 주문의 키)만 바꿉니다. 키 식별 번호만 적은 요청이나 갱신된 키를 환불했는데 요청이 그대로면 대시보드에서 '환불 완료'를 누르세요.
- 답장 알림 메일은 없습니다. 구매자는 앱이나 /help에서, 판매자는 대시보드에서 봅니다.

대시보드 '새 소식' (구매자가 한 일이 새로고침 없이 뜸)
- 구매자의 새 문의, 환불 요청, 답장, 닫은 문의에 다시 쓴 답장, 닫기와 웹훅이 마친 카드 환불마다 한 줄을 Durable Object(`src/stats.js`의 SQLite, KV 아님)에 남깁니다. 시각, 종류, 문의 번호, 문의 종류만 남기고 제목이나 글은 남기지 않습니다. 대시보드가 제목을 자기 문의 목록에서 찾습니다. 판매자가 한 일은 남기지 않습니다.
- 30일, 그리고 최근 1,000줄까지만 둡니다(새 줄을 쓸 때와 매시간 cron이 지웁니다). 문의를 지우면 그 문의의 줄도 지웁니다.
- 줄을 쓰다 실패해도 구매자의 요청은 그대로 됩니다(응답 뒤 `ctx.waitUntil`에서 쓰고, 실패는 무시).
- `GET /admin/api/support/feed?after=<번호>` → `{events, last, more}`: 그 번호 뒤의 줄을 오래된 것부터 100개까지. `after`가 없으면 최근 20개. 대시보드 비밀번호가 필요합니다. KV를 읽거나 쓰지 않고 Durable Object만 읽습니다.
- 대시보드는 탭이 화면에 보이는 동안 30초마다 묻고, 탭이 숨으면 멈췄다가 다시 보일 때 바로 한 번 묻습니다. 새 줄이 오면 문의 목록을 한 번 다시 불러와(KV 목록 1번) 고객센터 배지와 숫자를 바꾸고, 위쪽에 알림을 띄우고(누르면 그 문의가 열림), 탭 제목 앞에 `(N)`을 붙입니다(고객센터를 열면 사라짐). 고객센터 맨 위 '새 소식'에 최근 20개가 있고, 읽지 않은 것에 점이 붙습니다('모두 읽음'). 어디까지 읽었는지는 그 브라우저(localStorage)에 남습니다. '브라우저 알림 켜기'를 누르고 허락하면, 이 탭이 열려 있지만 다른 창을 보고 있을 때도 알립니다.
- 요청 수: 열어 둔 대시보드 하나가 하루 종일 화면에 보이면 30초마다 1번, 하루 2,880번입니다. Worker 요청과 Durable Object 요청이 그만큼씩 생기고, 대시보드 비밀번호 잠금 확인으로 KV 읽기가 2번씩(하루 5,760번, 무료 100,000번의 6%) 생깁니다. Workers 무료 플랜의 하루 100,000 요청은 라이선스 확인, 사용 통계 신호, 주문과 함께 쓰는 몫이고, 그중 2.9%입니다(PC와 휴대폰에 둘 다 열어 두면 5.8%). 탭을 숨기면 0입니다.
- KV 목록은 새 줄이 온 30초마다 1번(줄이 몇 개든 1번)이고, 아무 일도 없으면 0번입니다. 구매자 동작은 위의 하루 예산(쓰기 400번)으로 막혀 있어서, 하루 종일 공격이 들어오는 날에도 대시보드 하나에 400번쯤이 최대입니다(무료 플랜 하루 1,000번. 목록은 대시보드만 쓰므로 넘쳐도 구매자 쪽은 멈추지 않습니다). 열어 둔 문의에 구매자가 새로 쓰면 그 문의도 다시 읽습니다.
- Durable Object에는 구매자 동작마다 줄 하나를 씁니다(SQLite 무료 하루 100,000줄).

구독 관리 링크: 앱의 '구독 관리'는 `POST /support/subscription`으로 Lemon Squeezy 고객 포털 링크를 받아 엽니다. `LS_API_KEY`가 있어야 하고, Lemon Squeezy에서 읽기만 합니다. KV에는 쓰지 않습니다.
- 서버가 서명한 카드 구독 키만 됩니다. 막은 키(환불, 공유)와 지금 구독이 없는 키(`sub:<번호>`가 없음: 해지, 만료)는 잘못된 키와 같은 404입니다.
- 받은 링크는 구독마다 30분 동안 캐시와 메모리에 둡니다. 그동안 다시 눌러도 Lemon Squeezy에 묻지 않습니다. 같은 IP에서 한 시간에 20번까지입니다.

설정: 새로 할 일은 없습니다. 새 비밀 값도, 새 KV도, 새 바인딩도 없습니다('새 소식'은 이미 있는 `STATS` Durable Object에 표를 하나 더 만듭니다. 마이그레이션은 필요 없습니다).
- 대시보드에서 판매자 정보, 공지, 청약철회 기간(기본 7일), 자주 묻는 질문, 문의 받기를 바꿉니다(KV `config:support`).
- 판매자 정보는 비워 둘 수 있습니다. 비우면 '판매 페이지 참고'로 나옵니다.
- 자주 묻는 질문을 비우면 서버의 기본 질문이 나옵니다. 기본 질문은 이 README, 사용권 계약, 앱 문구에 있는 내용으로만 썼습니다.
- 청약철회 기간은 화면에 보여 주기만 합니다. 제9조 제1항의 7일과 다르게 두면 화면과 계약이 서로 다르게 보입니다.
- 사용권 계약 제9조나 앱 메뉴 이름을 바꾸면 `src/support.js`의 `ARTICLE_9`, `DEFAULT_FAQ`도 함께 고칩니다.
- 테스트: `node test_support.mjs`(새 소식은 `node test_stats.mjs`에도)

## 설치
1. `npm i -g wrangler` → `wrangler login`
2. `wrangler kv namespace create LICENSES` → `wrangler.toml`의 id 교체
3. 비밀 값 등록 (화면에 붙여 넣는 값은 아무에게도 보여 주지 마세요)
   - `wrangler secret put LICENSE_PRIVATE_KEY` ← systemboost-license-private.pem 내용 전체
   - `wrangler secret put ADMIN_TOKEN` ← 대시보드 비밀번호(6자 이상). 코드나 파일에는 적지 마세요
4. `wrangler deploy` → 나온 주소를 `wrangler.toml`의 `PUBLIC_URL`과 앱 `License.cs`의 `ServerUrl`에 넣고 앱을 빌드
5. `https://<주소>/admin`에 들어가 결제 링크를 넣으면 앱의 '결제하기'가 열립니다.

대시보드를 고쳤다면 `node build_admin.mjs`로 `src/admin_page.js`를 다시 만듭니다.
`admin/admin.html`을 파일로 바로 열면 가짜 데이터로 움직이는 시연 모드가 됩니다.

## 카드 자동 결제 — Lemon Squeezy
카드 등록 · 매달(매년) 자동 청구 · 환불 · 세금 처리를 Lemon Squeezy가 하고, 결제되면 웹훅으로 키가 자동 발급됩니다(판매자 확인 없이).
1. Lemon Squeezy에서 구독 상품을 플랜마다 하나씩(월간, 연간, 울트라 월간, 울트라 연간) 만듭니다.
2. 바탕화면 `SystemBoost 카드 결제 키 넣기.cmd`로 API 키와 웹훅 서명 비밀을 직접 넣습니다(`wrangler secret put LS_API_KEY`, `LS_SIGNING_SECRET`).
3. Settings → Webhooks에 대시보드 '카드 결제 설정'에 나온 주소를 넣고, 이벤트 `subscription_created`, `subscription_updated`,
   `subscription_payment_success`, `subscription_payment_refunded`, `order_refunded`를 고릅니다. 서명 비밀은 2번과 같은 값.
4. 대시보드 '카드 결제 설정'에 상점 번호와 플랜별 상품(variant) 번호를 넣습니다. 비워 둔 플랜은 카드로 팔지 않습니다.
5. 대시보드 카드 결제 '테스트' → 앱에서 '카드로 결제하기' → Lemon Squeezy 테스트 카드로 결제 → 키(24시간짜리)가 자동으로 뜨는지 확인
6. '실판매'로 바꾸면 실제 카드 결제가 열립니다. 테스트 모드의 상품 번호와 API 키는 실판매에서 쓸 수 없으니 실판매 것으로 다시 넣습니다.
   앱에는 사용권 계약의 카드 구독 조항(제3조 제3항)이 시행되는 2026년 12월 8일 0시(한국 시간)부터 나옵니다. 그 전에 '실판매'로 두어도 앱에는 카드 결제가 나오지 않습니다 (`CARD_LIVE_FROM`, src/index.js).

어떤 플랜인지는 Lemon Squeezy가 서명해서 보내는 상품 번호로만 정합니다. 결제창 주소의 custom 값은 구매자가 바꿀 수 있어서
주문 코드를 찾는 데만 씁니다. 첫 결제는 `subscription_created` 한 번으로 키 하나, 갱신은 `subscription_payment_success`(renewal)마다 새 키,
고객 포털에서 플랜을 바꾸면 `subscription_updated`로 바뀐 플랜의 키가 나갑니다. 첫 결제나 갱신을 환불하면 그 키를 차단합니다.
